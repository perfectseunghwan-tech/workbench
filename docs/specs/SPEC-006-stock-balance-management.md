# SPEC-006: 증권사·계좌별 주식잔고 관리

## 1. 목적과 범위

증권사·계좌·종목별 현재 보유 현황을 직접 입력하고, 저장된 매수·매도 거래를 선택하여 **한 번에** 잔고에 반영하는 기능의 구현 방안을 정한다. 같은 계좌·종목에 여러 거래가 있더라도 반영 시 평균 매입가는 한 번만 수기로 입력한다. 이 문서는 구현 전 명세이며, 작성 단계에서는 애플리케이션 소스와 데이터베이스를 변경하지 않는다.

## 2. 현재 구현 구조

### Backend

- Spring Boot 3.2.4, Java 21, PostgreSQL을 사용한다. 데이터 접근은 `NamedParameterJdbcTemplate` 기반 Controller → Service → Repository 구조다.
- `StockTradeController`의 `/api/stock-trades`는 거래 목록·상세·등록·수정·삭제를 제공한다. `StockTradeService`는 `BUY`·`SELL`, 사용 중인 계좌·종목, 양수 수량 등을 검증하고 `StockTradeRepository`는 `stock_trade`만 변경한다. 현재 잔고 반영이나 반영 이력 관리는 없다.
- `GET /api/brokerages`, `/api/investment-accounts?brokerageId=`, `/api/stocks`는 거래 화면용 기준정보를 제공한다. 거래 목록은 증권사·계좌·종목 필터와 서버 페이징을 지원한다.
- 계좌 삭제는 현재 해당 계좌의 거래와 메모를 삭제한 다음 계좌를 삭제한다. 종목 삭제의 사전 검사는 거래 참조만 확인한다. 잔고가 생기면 이 경로도 검토해야 한다.

### Frontend

- Vue 3·TypeScript·PrimeVue를 사용한다. `StockTradeView.vue`와 `stockTradeApi.ts`에서 거래 CRUD 및 증권사·계좌·종목 선택을 처리한다.
- `AppShell.vue`와 `router/index.ts`에 주식잔고 메뉴·화면은 없다. 관리 화면은 DataTable과 공통 디자인 토큰·컴포넌트 스타일을 사용한다.

### DB

- 사용자 제공 DDL 기준으로 `public.stock_balance`는 `(account_id, stock_id)` 유일 제약을 가진 현재 잔고다. 수량과 매도가능수량, 현재가, 평균 매입가, 매입금액, 평가금액·손익·수익률, 잔고 기준 시각을 저장한다.
- `public.stock_balance_snapshot`은 `(account_id, snapshot_at)` 유일 제약을 가진 계좌별 시점 헤더이고, `public.stock_balance_snapshot_detail`은 `(snapshot_id, stock_id)` 유일 제약을 가진 종목별 상세다. 상세는 헤더 삭제 시 연쇄 삭제된다.
- 세 테이블은 이미 DB에 생성되었다는 사용자 제공 정보에 따른다. 저장소의 `backend/src/main/resources/schema.sql`에는 이 세 테이블의 DDL이 없고 전략·거래 연결 테이블만 있다. 실제 DB 접속 및 현존 데이터 확인은 이 분석에서 하지 않았다.
- 제공된 세 테이블에는 어떤 `stock_trade.trade_id`가 잔고에 이미 반영됐는지 기록할 컬럼·관계가 없다. 중복 반영 방지를 위해 별도 반영 이력이 필요하다.

## 3. 요구사항과 확정 동작

1. 증권사와 계좌로 현재 잔고를 조회하고, 종목별 잔고를 직접 등록·수정한다. 목록에 증권사·계좌·종목명·종목코드와 모든 잔고 수치 및 기준 시각을 표시한다. 사용 중지된 계좌·종목의 기존 잔고도 조회할 수 있다.
2. 직접 입력은 특정 계좌·종목의 **현재값 전체를 대체**한다. 수량은 필수 0 이상, 나머지 수치 필드는 선택 입력이다. `purchase_price`는 자동 계산하지 않는다. `purchase_amount`, 평가 관련 값도 입력값을 보존하며 묵시적으로 재계산하지 않는다.
3. 거래 등록 시 거래 자체만 저장한다. 사용자는 미반영 거래 목록에서 거래를 선택한 후 명시적인 **잔고 반영** 작업을 실행한다. 선택 거래는 계좌·종목별로 묶고, 각 묶음에 평균 매입가를 한 번 입력할 수 있게 한다. 반영 작업은 선택한 거래 전부에 대해 원자적으로 성공하거나 전부 실패한다.
4. 각 묶음의 수량 변화는 `BUY` 합계에서 `SELL` 합계를 뺀 값이다. 기존 잔고 수량에 이를 가감한다. 잔고가 없으면 0에서 시작한다. 결과가 음수면 전체 작업을 거절한다. 결과가 0이어도 잔고 행은 유지하여 중복 반영과 이후 직접 수정을 일관되게 다룬다.
5. 평균 매입가는 묶음별 사용자가 제출한 값이 있으면 그 값으로 한 번 갱신한다. 비우면 기존 값을 유지하고, 신규 잔고에서는 `NULL`로 둔다. 거래 자체의 `purchase_price`는 평균 매입가로 사용하지 않는다. `available_quantity`는 결제·매도 가능 여부를 거래만으로 확정할 수 없어 거래량으로 자동 가감하지 않는다. 수량 변경 후 기존 매도가능수량이 새 잔고수량을 초과하면 `NULL`로 비워 직접 재입력하도록 한다. 현재가는 유지하고, 수량에 종속된 매입금액·평가금액·평가손익·수익률은 수량이 바뀌면 `NULL`로 비워 직접 보완하도록 한다.
6. 동일 거래는 한 번만 반영된다. 과거 거래를 자동으로 일괄 적용하지 않는다. 미반영 거래 중 사용자가 선택한 건만 반영하므로 기존 직접 입력 잔고를 과거 거래로 중복 계산하지 않는다.
7. 이미 반영된 거래를 수정하거나 삭제하면, 동일 DB 트랜잭션에서 기록된 이전 수량 효과를 되돌리고 수정된 거래의 효과를 재적용하거나 삭제 효과만 반영한다. 수정으로 계좌·종목·매수/매도·수량이 바뀌면 이전 묶음과 새 묶음을 모두 처리한다. 결과가 음수인 경우 거래 변경 전체를 거절한다. 반영되지 않은 거래 수정·삭제는 기존 동작대로 잔고에 영향을 주지 않는다. 평균 매입가는 자동 재계산하지 않으며 필요하면 사용자가 보정한다.
8. 잔고가 실제로 바뀌는 직접 저장·일괄 반영·반영 거래 수정/삭제가 성공하면 영향받은 계좌마다 현재 잔고 **전체**의 스냅샷을 남긴다. 스냅샷은 과거 조회용 읽기 전용이며 현재 잔고 수정의 근거로 재적용하지 않는다.

## 5. Backend 변경

- `/api/stock-balances`에 증권사·계좌·종목 필터를 받는 현재 잔고 조회, 계좌·종목 잔고 직접 저장, 계좌별 스냅샷 목록·상세 조회를 제공한다. 직접 저장은 `(accountId, stockId)` 기준 upsert이며 클라이언트가 전달한 `balanceUpdatedAt` 대신 서버 시각을 기록한다. 동시 갱신은 계좌 행 잠금 등으로 직렬화한다.
- `/api/stock-balance-applications/preview`에 선택한 `tradeIds`를 보내 계좌·종목별 매수/매도 합계, 기존·예상 수량, 반영 여부를 확인한다. `/api/stock-balance-applications`에 같은 거래 ID 목록과 계좌·종목별 선택적 `purchasePrice`를 보내 일괄 반영한다. 서버에서 수량을 다시 계산하고, 선택 건에 이미 반영된 거래가 하나라도 있으면 충돌 응답을 준다. 입력 거래 ID의 중복·누락, 비활성 계좌/종목, 숫자 범위도 검증한다.
- 미반영 거래 조회는 기존 거래 API에 `balanceApplied` 필터 및 응답 필드를 추가하거나 별도 조회 엔드포인트를 제공한다. 기존 필터·페이징·정렬 기본값 및 기존 필드는 유지한다. 사용 중지된 기존 거래는 조회 가능하게 하되 새 반영 대상은 현재 활성 기준정보만 허용한다.
- 잔고 DTO의 숫자는 `BigDecimal`, 시각은 `LocalDateTime`으로 다룬다. `numeric(20,6)`, `numeric(24,2)`, `numeric(12,6)`의 허용 정밀도·스케일과 0 이상 제약을 Service에서 검사하여 DB 오류 대신 명확한 4xx를 반환한다. `available_quantity`가 입력되면 잔고수량 이하인지도 검증한다.
- 거래 수정·삭제 시 반영 이력을 조회해 이전 적용량을 역산하고, 수정 거래의 새 적용량을 기록한다. 관련 계좌·잔고를 일정한 순서로 잠가 데드락·이중 반영을 방지한다. 잔고, 반영 이력, 거래, 스냅샷 쓰기는 하나의 `@Transactional` 경계에 둔다.
- 계좌 삭제 시 잔고·스냅샷·반영 이력이 있는 계좌는 명확한 충돌 응답으로 막는다. 종목 삭제도 잔고 또는 스냅샷 참조를 확인하여 사용 중지로 유도한다. 계좌 사용 중지나 종목 사용 중지는 기존 잔고·이력을 삭제하지 않는다.

## 6. Frontend 변경

- 별도 주식잔고 화면을 라우터와 사이드바에 추가한다. 증권사 → 계좌 선택, 종목 검색, 현재 잔고 표, 계좌별 합계와 스냅샷 열람, 직접 입력·수정 폼을 제공한다. 여러 통화가 섞인 합계는 통화별로 나누고 단순 합산하지 않는다.
- 거래 화면에 미반영 거래 선택 후 잔고 반영으로 이동하는 동선을 추가한다. 반영 화면에서 선택 거래를 계좌·종목별로 묶어 예상 수량을 보여주고, **거래별이 아닌 묶음별 평균 매입가 입력란 하나**를 제공한다. 제출 후 잔고와 거래 목록을 새로 조회한다.
- 서버 오류(이미 반영됨, 잔고 부족, 비활성 기준정보, 동시 수정)를 표시하고 입력값을 유지한다. 선택 계좌에 속하지 않는 종목·거래를 잘못 반영하지 않도록 화면 상태를 관리하되 서버 검증을 최종 기준으로 삼는다.
- 기존 `stockTradeApi.ts`의 기준정보 호출과 공통 DataTable·패널·컨트롤 스타일을 재사용한다. 재사용 디자인 값은 `design-tokens.css`, 공통 모양은 `ui-components.css`에 두고 화면 CSS는 화면 고유 배치에 한정한다.

## 7. DB 변경

- 제공된 `stock_balance`, `stock_balance_snapshot`, `stock_balance_snapshot_detail`은 재생성하거나 변경하지 않는다. 배포 전 실제 DB에 제공 DDL과 제약·인덱스가 존재하는지 확인한다. `schema.sql`은 현재 위 세 테이블의 생성 근거가 아니므로 기존 테이블을 다시 만드는 초기화 SQL을 넣지 않는다.
- 중복 반영 및 거래 정정을 위해 `stock_balance_trade_application`을 새로 추가한다. 최소 컬럼: `trade_id`(PK, `stock_trade` FK), 적용 당시 `account_id`, `stock_id`, `trade_type`, `applied_quantity numeric(20,6)`, `applied_at`, `updated_at`. `trade_type`과 수량은 적용 당시 효과를 되돌리는 근거이며 양수 수량·BUY/SELL 제약을 둔다. 거래 삭제 시에는 서비스가 먼저 이력을 읽고 잔고를 정정한 뒤 이력과 거래를 같은 트랜잭션에서 삭제한다. FK는 실수로 이력만 남기는 일을 막는다.
- 위 추가 테이블은 제공 DDL만으로는 요구사항의 **한 번만 반영**을 보장할 수 없어 필요한 최소 확장이다. 기존 데이터에 대한 자동 소급 반영·마이그레이션은 하지 않는다. 실행할 DDL은 구현 단계에서 프로젝트의 배포 방식에 맞춰 별도 검토하며 이 명세 작성 시 실행하지 않는다.
- 각 스냅샷 헤더 생성 시 같은 트랜잭션에서 그 계좌의 현재 `stock_balance` 행 전체를 상세에 복사한다. `snapshot_at` 중복은 DB 유일 제약에 맞춰 충돌 없이 생성하도록 처리한다. 기존 스냅샷을 수정·삭제하지 않는다.

## 8. 기존 동작 유지 조건과 구현 제약

- 거래 CRUD API의 기존 요청·응답 필드와 계산된 `execution_amount`, 검색·페이징 동작을 유지한다. 신규 거래 등록만으로 잔고가 변하지 않는다.
- 직접 입력한 잔고와 거래 반영 잔고는 같은 `(account_id, stock_id)` 행을 사용한다. 직접 입력을 과거 거래 집계로 다시 덮어쓰지 않는다.
- 평균 매입가, 매입금액, 평가액·손익·수익률을 거래 내역에서 추정하거나 자동 산출하지 않는다. 수량 변경으로 비워진 값은 사용자가 다시 입력한다. 통화 간 금액도 합치지 않는다.
- 잔고·스냅샷·반영 이력을 삭제하는 기능은 이번 범위에 넣지 않는다. 직접 입력으로 수량을 0으로 만드는 것은 허용한다.
- 사용자가 제공한 DDL과 실제 운영 DB의 차이, 기존 잔고와 과거 거래의 정합성은 DB 확인 없이는 단정하지 않는다. 구현 전 실제 스키마와 데이터 상태를 확인해야 한다.

## 9. 검증 방법

1. 직접 입력으로 같은 계좌·종목에 한 행만 생기고 입력 숫자·NULL·기준 시각이 유지되는지 확인한다.
2. 같은 종목의 매수·매도 여러 건을 한 번에 반영해 순수량이 맞고 평균 매입가 입력이 한 번만 적용되는지 확인한다. 다른 계좌의 동일 종목은 독립적으로 처리한다.
3. 같은 거래의 재반영, 음수 잔고, 범위 초과 숫자, 일부만 유효한 일괄 요청이 모두 전체 롤백되는지 확인한다.
4. 반영 전후 거래 수정·삭제, 계좌·종목 변경을 검증하고 적용량·이력·스냅샷의 일관성을 확인한다. 직접 입력 이후 반영 거래 정정 시 음수 방지도 확인한다.
5. 각 성공 변경에 계좌 전체 스냅샷이 한 번 생성되고 이후 직접 입력이나 거래 변경에도 과거 상세가 변하지 않는지 확인한다.
6. 계좌·종목 삭제 보호와 사용 중지 후 기존 잔고 조회, 기존 거래 API·화면 회귀를 확인한다.
7. 구현 시 변경 파일 포맷, 타깃 Backend 테스트·컴파일, Frontend 타입 검사·빌드를 실행한다. 서버를 시작해야 하는 실제 DB·브라우저 검증은 별도 실행 지시가 있을 때 수행한다.
