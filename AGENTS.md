# Workspace Rules

## 1. Workspace

The active development workspace is:

`C:\workbench\`

Codex may read, create, modify, rename, and delete files inside this workspace
when required to complete the user's requested task.

All file modifications must remain within `C:\workbench\`.

The external attachment directory is:

`C:\Users\itumo\.codex\attachments\`

- Codex may read files in this directory to analyze user-provided requirements
  and reference materials.
- Treat all attachment files as read-only.
- Do not create, modify, rename, move, or delete files in the attachment directory.
- If reading an attachment requires additional permission, request the necessary
  authorization.
- Do not expand writable permissions merely to read attachments.
- If an attachment cannot be accessed, report the actual error rather than
  assuming its contents.
- Never modify other files outside the active workspace.

## 2. Project Structure

The workspace contains the application source and development specifications.

Primary structure:

`C:\workbench\`

- `backend\` — backend application
- `frontend\` — frontend application
- `docs\specs\` — approved feature specifications and implementation plans
- `AGENTS.md` — default Codex development rules

Files under `docs\specs\` are the primary implementation specifications when
explicitly referenced by the user.

`AGENTS.md` defines how Codex must work.

`docs\specs\*.md` defines what Codex must implement for a specific task.

## 3. Instruction Priority

Apply instructions in the following order:

1. User's explicit instruction for the current task.
2. The referenced specification under `docs\specs\`.
3. This `AGENTS.md`.
4. Existing project architecture, conventions, and implementation patterns.

A specification does not authorize unrelated changes.

Permission to modify the workspace does not mean that unrelated files should
be modified.

If a specification conflicts with the actual source structure:

- Preserve the intent and functional requirements of the specification.
- Follow the actual project structure and existing implementation patterns.
- Make the smallest reasonable deviation.
- Report the deviation after implementation.

If requirements remain materially ambiguous and implementation would require
guessing about business behavior, stop and ask the user rather than inventing
requirements.

## 4. Allowed Work

Codex may perform the following operations within the workspace when relevant
to the user's requested task:

- Inspect existing source code and project structure.
- Search for relevant files, functions, components, APIs, and database objects.
- Read referenced files under `docs\specs\`.
- Create and modify frontend and backend source files.
- Create and modify tests.
- Create and modify SQL/DDL scripts.
- Update project configuration when required.
- Update project documentation when required.
- Run builds, static analysis, compilation, and tests related to the requested task.
- Create temporary validation files within the workspace when necessary.
- Remove temporary files generated by its own work when safe.

Only perform operations necessary to complete the requested task.

Do not treat general workspace access as authorization to make unrelated changes.

## 5. Source Analysis

Before making changes:

1. Read the user's request and any explicitly referenced specification.
2. Identify the likely affected module, directories, and files.
3. Inspect the existing implementation related to the requested functionality.
4. Identify the minimum set of affected files.
5. Understand relevant dependencies and data flow.
6. Check related API contracts and database objects when applicable.
7. Follow existing architecture, coding standards, and conventions.
8. Reuse existing components, services, utilities, APIs, DTOs, and libraries
   where practical.

### Source exploration rules

- Do not scan or read the entire repository unless necessary.
- Search likely affected directories and files first.
- Follow symbols, imports, references, API calls, and call chains only as needed.
- Expand the search scope incrementally when dependencies require it or the
  relevant implementation cannot otherwise be identified.
- Do not repeatedly scan the entire project.
- Do not repeatedly read files that have already been sufficiently understood.
- Prefer targeted searches and relevant file sections instead of reading entire
  large files.
- Reuse source information already obtained during the current task.
- Do not repeatedly analyze unchanged architecture or configuration.

Exclude the following from broad source searches unless explicitly required:

- `node_modules`
- `.git`
- `dist`
- `build`
- `coverage`
- generated files

## 6. Specification-Driven Implementation

When the user references a file under `docs\specs\`:

1. Read the referenced specification before modifying source code.
2. Treat the specification as the primary functional requirement for the task.
3. Verify the specification against the actual current source before editing.
4. Identify which parts are:
   - already implemented,
   - partially implemented,
   - not implemented,
   - or inconsistent with the current source.
5. Implement only the changes required to satisfy the specification.
6. Preserve existing compatible functionality.
7. Do not broaden the implementation beyond the specification.
8. Do not redesign unrelated architecture.
9. Do not add speculative functionality that is not required by the specification.
10. Report any necessary deviation from the specification after implementation.

The specification may describe expected files or components.

If those names differ from the actual project:

- Do not create duplicate architecture merely to match the document.
- Use the actual existing structure.
- Preserve the specification's functional intent.

## 7. Planning-Only Requests

When the user explicitly requests analysis, review, investigation, design, or
implementation planning only:

- Inspect only relevant source files and reference materials.
- Compare the requirement with the current implementation.
- Identify existing, partial, and missing functionality.
- Identify affected frontend, backend, database, and configuration areas.
- Propose a concise implementation approach.
- Define appropriate verification criteria.
- Identify material risks, dependencies, and unresolved assumptions.
- Do not modify application source files.
- Do not execute database changes.
- Do not start development servers.
- Do not begin implementation unless explicitly requested.

If the user asks Codex to create or update a specification under `docs\specs\`,
only that specification file may be written unless additional changes are
explicitly requested.

## 8. Implementation Rules

When implementation is requested:

- Make the smallest change necessary to satisfy the requirement.
- Modify only files directly required by the task.
- Follow the referenced specification when one exists.
- Preserve existing APIs, business logic, routing, and database behavior unless
  changes are explicitly required.
- Preserve existing implementation patterns unless there is a clear technical
  reason to change them.
- Reuse existing components, styles, utilities, services, and DTOs where practical.
- Do not perform unrelated refactoring.
- Do not reorganize unrelated files or directories.
- Do not introduce unnecessary abstractions.
- Do not add new frameworks or dependencies unless required.
- Do not remove existing functionality unless explicitly required.
- Implement changes in small, logically related units.

### Database changes

- Do not modify the database schema unless required by the task or specification.
- When schema changes are required, create or provide the appropriate DDL or
  migration according to the project's existing approach.
- Do not execute destructive database operations unless explicitly authorized.
- Do not drop or truncate existing tables without explicit authorization.

## 9. File Access and Command Execution

The primary execution environment is Windows.

Use Windows-compatible commands, preferably PowerShell, when shell commands
are required.

Before executing commands:

- Confirm the intended working directory.
- Use explicit file paths when necessary.
- Quote paths containing spaces or special characters.
- Prefer read-only inspection commands during analysis.
- Avoid unnecessarily broad recursive operations.

Useful inspection commands include:

- `Get-Location`
- `Get-ChildItem`
- `Get-Content`
- `Test-Path`
- `rg --files`
- `rg`

When command execution fails:

1. Determine whether the failure occurred during environment initialization or
   after the command started.
2. Distinguish Sandbox initialization failures from filesystem permission failures.
3. Distinguish missing commands or invalid paths from execution environment failures.
4. Retry with a simpler read-only command when appropriate.
5. Do not repeatedly run the same failing command without changing the diagnostic
   approach.
6. Do not modify Sandbox configuration or disable security restrictions automatically.
7. Do not assume a command succeeded without confirming the result.
8. Report the actual error and the operations that could not be completed.

If shell execution remains unavailable, use permitted alternative inspection
capabilities when available.

Never claim that source analysis or verification was completed if the required
files could not actually be accessed.

## 10. Verification Strategy

Use the minimum verification appropriate to the change.

Verification must be proportional to the implementation risk.

### General rules

- Verify changed files and their direct dependencies first.
- Prefer targeted compilation, tests, linting, type checking, or static checks.
- Do not automatically run full-project builds or complete test suites.
- Run broader validation only when:
  - targeted verification fails,
  - shared or core functionality changed,
  - the change has significant regression risk,
  - or the user explicitly requests broader verification.
- Do not repeatedly execute identical tests when the relevant code has not changed.
- Do not start long-running processes unless explicitly requested.
- Prefer non-interactive verification commands.
- Never report tests as passed unless they were actually executed successfully.

### Frontend verification

For frontend modifications, choose only the checks relevant to the change,
when configured and necessary:

- relevant unit tests
- lint checks
- type checks
- `npm run build`
- other existing project-specific validation scripts

Do not run `npm run dev` unless explicitly requested.

Do not automatically start the frontend development server.

Do not perform browser-based runtime testing that requires starting the
development server unless explicitly requested.

### Backend verification

For backend modifications:

- Prefer targeted compilation or build checks.
- Run relevant unit tests when available.
- Use targeted validation before broader test execution.
- Do not automatically start a persistent backend server.
- Expand validation only when justified by the affected scope.

### Database verification

For database-related changes:

- Review SQL syntax and schema compatibility.
- Verify expected impact on existing tables and data.
- Prefer non-destructive validation.
- Do not automatically execute migrations unless explicitly requested.
- Do not execute destructive DDL or DML without explicit authorization.

### Runtime verification limitations

If adequate verification requires starting a development server:

- Do not start it automatically unless explicitly requested.
- Explain what could not be runtime-verified.
- Provide the relevant command or manual verification procedure if useful.
- Mark the affected functionality as not runtime-verified.

## 11. Efficient Token and Time Usage

Codex should minimize unnecessary source exploration, reasoning repetition,
command execution, and verification work without sacrificing correctness.

- Do not repeat analysis or planning already established in the referenced
  specification.
- Do not redesign requirements already decided in `docs\specs\`.
- Do not repeat architectural analysis unless the actual source contradicts the
  specification or implementation requires additional investigation.
- Do not read large files in full when targeted sections are sufficient.
- Do not repeatedly read unchanged files.
- Do not repeatedly execute the same command without a technical reason.
- Avoid full-project builds and test suites for localized changes.
- Expand analysis and verification incrementally.
- For straightforward implementation tasks, proceed after targeted inspection.
- For complex tasks, establish only a concise implementation sequence before editing.
- Do not sacrifice correctness, security, or necessary verification merely to
  reduce token usage.

## 12. Development Restrictions

Do not:

- Modify files outside `C:\workbench`.
- Modify or delete external attachment files.
- Delete unrelated source files or directories.
- Modify credentials, secrets, passwords, tokens, or private keys.
- Expose sensitive information in logs or reports.
- Change dependency versions unless required by the requested task.
- Install new packages unless required by the requested task.
- Perform destructive database operations without explicit authorization.
- Drop or truncate existing database tables without explicit authorization.
- Make unrelated architectural changes.
- Perform broad refactoring unrelated to the task.
- Remove existing functionality without a clear requirement.
- Override Sandbox security settings to bypass execution failures.
- Run destructive Git commands without explicit authorization.
- Overwrite existing user changes without first examining their contents and
  relevance.

## 13. Completion Report

After implementation, report concisely:

1. **Summary** — what was implemented or changed.
2. **Modified files** — files created, updated, or deleted.
3. **Key changes** — important implementation details.
4. **Validation** — commands/checks actually executed and their results.
5. **Not validated** — relevant tests or runtime checks that were not performed.
6. **Specification deviations** — deviations from the referenced specification,
   if any.
7. **Limitations / risks** — unresolved issues, assumptions, or known risks.

Do not include sections with meaningless filler.

For a simple change, keep the completion report short.

For planning-only work, report only information necessary to support the next
design or implementation decision.
